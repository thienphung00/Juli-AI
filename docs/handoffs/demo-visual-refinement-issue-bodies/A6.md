## What to build
Make Settings a **visitor-disabled placeholder** for the public Demo: keep Settings in bottom/side navigation but disable interaction using the same accessible pattern as the Sign-in stub (`aria-disabled`, visible explanation, no navigation to editable config).

Replace or gate the current interactive Settings tabs/forms so visitors see an honest placeholder — not a half-polished configuration surface.

### Primary paths
- `apps/demo/src/components/settings-view.tsx`
- `apps/demo/src/components/settings-workflow-detail.tsx`
- `apps/demo/src/components/settings-thresholds-panel.tsx`
- `apps/demo/src/components/demo-shell.tsx` (Sign-in stub precedent)
- `apps/demo/src/__tests__/settings-workflows.test.tsx`, `settings-workflow-detail.test.tsx`

## Acceptance criteria
- Settings nav destination remains discoverable in four-destination shell
- Settings page/content is non-interactive for visitors with `aria-disabled` or equivalent accessible disabled pattern matching Sign-in stub behavior
- Visible Vietnamese placeholder explains configuration requires Sign-in (or equivalent honest copy per `dictionary.md`)
- No navigation to editable workflow templates, thresholds, or save flows from the disabled Settings surface
- Tests assert disabled state and explanation; no regression to Sign-in stub pattern
- Focus order and aria labels preserved

## Out of scope
- Settings configuration UI polish (templates, thresholds, workflow editors)
- Threshold validation, save persistence, or workflow detail editing UX
- In Progress sub-tab changes
- Home, Analytics, or Recommendations visual work
- Sign-in/OAuth implementation (Phase 3)
